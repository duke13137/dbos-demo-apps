Lesson 1 Trace-driven DBOS reading

DBOS is a workflow context machine, not just a function wrapper.

In this app, the important move is not “call a Python function and print a status.” It is “enter a DBOS workflow context, snapshot it at each step, and persist the step state so the workflow can pause, resume, and be queried later.”

What the trace teaches

Follow one request across three layers

The trace shows the same workflow instance passing through the app layer, the DBOS wrapper layer, and the DBOS context layer. That is the core design idea: each important transition is tied to a workflow id and a step id.

Hop Source Meaning
1 main.py:73-82 The workflow creates an AgentStatus, stores it, marks it pending_approval, then blocks on DBOS.recv().
2 dbos/_dbos.py:1712-1718 DBOS.set_event() checks context and hands off to the core implementation.
3 dbos/_context.py:392-397 snapshot_step_context() returns a workflow-scoped context snapshot.
4 dbos/_context.py:249-256 start_step() advances the step id and creates a fresh StepStatus.
5 dbos/_core.py:1976-2000 The event write is committed using the active workflow context.
6 dbos/_dbos.py:1538-1557 recv() uses the same context to suspend until approval or timeout.
The useful mental model is simple: workflow id answers “which instance?”, step id answers “which resumable hop?”, and events are the durable state you can query from the UI.
Implementation map

Where the behavior lives

  • App layer: main.py starts the workflow, updates status, and responds to approval.
  • Wrapper layer: dbos/_dbos.py validates the context and dispatches durable operations.
  • Context layer: dbos/_context.py snapshots and advances workflow step state.
  • Core layer: dbos/_core.py performs the actual event write and wait logic.
